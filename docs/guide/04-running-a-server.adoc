= Running a server

The JXPilot server runs the game: the simulation ported from the XPilot server, robots, and the
network layer that JXPilot clients connect to. It is headless and runs on any system with Java 25.
Alliances and the `/` commands are not on it yet (<<01-introduction.adoc#status,Status>>).

[[server-cli]]
== Command line

[source,shell]
----
java [JVM options] -jar jxpilot-server-VERSION.jar [--map MAP] [--port N] [--bind SELECTOR ...] [--bindWait]
     [--defaults FILE|none] [-OPTION VALUE ...] [CONFIGFILE]
java -jar jxpilot-server-VERSION.jar --list-maps
java -jar jxpilot-server-VERSION.jar -help | -version | -dump | -dumpMan | -dumpWindows | -dumpFlags
----

Like the original XPilot server, the server quits when the last human player has left (or when nobody has
joined after 5 minutes). Pass `-noQuit` (or put `noQuit: yes` in the config file) for a server that keeps
running.

`--map MAP`:: The map to serve (here or as `mapFileName` in the config file): the name of a map built
into the jar, such as `default` or `tourmination`, or the path of an XPilot `.xp` file. Without it the
server plays the built-in `default`, as the C server plays its `default.xp`. See <<map-selection>>.
`--list-maps`:: Print the maps built into the jar, with their size, title and author, and exit.
`--port N`:: The UDP port to listen on, default 15345 (option `contactPort`).
`--bind SELECTOR`:: Which local addresses to listen on, default `all`. Repeat it or give a comma list:
`--bind tailscale0 --bind loopback` is the same as `--bind tailscale0,loopback`. See <<binding>>.
`--bindWait`:: Start even if a `--bind` selector matches no address yet, and bind it when it appears
(for example when a VPN comes up after the server). See <<bind-wait>>.
`--defaults FILE|none`:: The defaults file read before the config file and the map: XPilot's
`lib/defaults` unless you name another file, or none at all (<<defaults-file>>). Option
`defaultsFileName`.
`-OPTION VALUE`:: Any server option, by its name or short name, for example `-gravity -0.3`,
`--maxClientsPerIP 8` or `-FPS 20`. All options are listed in
<<05-server-options.adoc#server-options,Server configuration reference>>.
`CONFIGFILE`:: One server configuration file (<<config-files>>). Anything on the command line that is
not an option is taken as the config file name; two such arguments are an error.

[[cli-syntax]]
=== Option syntax

* An option is `-name value` or `--name value`. Names are matched without regard to case or spaces,
  and the short name works as well as the full name: `-port`, `--contactPort` and `-CONTACTPORT` are
  the same option.
* *Boolean options take no value.* `-name` (or `--name`) turns it on, `+name` turns it off:
  `-teams` turns team play on, `+edgeWrap` turns wrapping off.
+
CAUTION: `-teams yes` does not do what it looks like: `-teams` turns team play on, and `yes` is then
taken as the config file name, which fails to load (the server prints `jxpilot server: yes` and exits).
* Text and list values containing spaces need shell quoting: `-mapName "My map"`.
* A value that does not parse (for example `-port abc`) is reported as an "option warning" at startup
  and the option keeps its default.

[[info-requests]]
=== Information requests

These print something and exit, as the XPilot server does (one or two dashes):

[cols="2,4",options="header"]
|===
|Flag |Prints
|`-help`, `-h` |Every option with its short name, value type, help text and where it may be set.
|`-version`, `-v` |`JXPilot server VERSION (a port of XPilot 4.5.5)`.
|`-dump` |Every option with its built-in default, in config-file format: a starting point for a
config file.
|`-dumpMan`, `-dumpWindows` |The same as `-dump` (XPilot's own formats for these are not reproduced).
|`-dumpFlags` |Every option's allowed sources and visibility.
|===

[[exit-status]]
=== Exit status and stopping

The server runs until it is stopped with kbd:[Ctrl+C] or `SIGTERM`, also when every player has left,
or, with `gameDuration`, until 30 seconds after the game is over: then it logs
`game over: shutting down`, disconnects every player and exits with status 0.
(XPilot's server exits when the last human leaves, unless started with `-noQuit`; matching that is
being worked on.) It then tells connected players
it is going away, closes its sockets and exits; as for any Java program, the exit status is then 130
(after kbd:[Ctrl+C]) or 143 (after `SIGTERM`). It exits with status 1 for bad arguments, a missing or
unreadable map, or a bind failure (with the reason and a usage line on standard error), and with
status 2 if the server loop fails while running.

[[jvm-options]]
=== Java options

The server needs no special Java options. The recommended collector is ZGC, which keeps pauses short:
`java -XX:+UseZGC -jar jxpilot-server-VERSION.jar ...`. Memory use is small; `-Xmx256m` is plenty for
a normal game.

[[server-output]]
=== What the server prints

Startup and connection events go to standard error, one line each:

----
listening on 10.224.0.16:15345 (utun4)          <1>
listening on 127.0.0.1:15345 (lo0)
serving map 'The Newbie Globe' (170x170 blocks) at 12 frames/s   <2>
join: player 1 'alice' from /10.224.0.20:53122 on channel 0      <3>
leave: player 1 (timeout)
----
<1> One line per bound address, with its interface. Tell players these addresses.
<2> The map and the simulation rate, which is the map's `framesPerSecond`.
<3> Players joining and leaving. Robots are not logged.

Option problems appear as `option warning: ...`, binding problems as `bind warning: ...`, and changes
found by the interface rescan as `listening on ...`, `unbound ...` or `interface renamed: ...`.

[[map-selection]]
== Choosing the map

The map comes from `--map` (or `mapFileName: MAP` in the config file); with neither, it is the built-in
`default` ("The Newbie Globe"). A map file holds the map
itself (`mapData`) and usually options for it, such as `gravity` or `teamPlay`
(<<06-config-and-maps.adoc#config-and-maps,Config and map files>>). The 19 maps that come with
JXPilot are built into the jar and listed in <<06-config-and-maps.adoc#shipped-maps,Shipped maps>>
(and by `--list-maps`); any XPilot 4.5.5 block-based map file should work too.

[[map-names]]
The value of `--map` is read like this:

* A plain name, without `/` or `\` (and no drive letter such as `C:`), is a map built into the jar.
  `tourmination`, `tourmination.xp` and `Tourmination` are the same map. Nothing on disk is needed.
* A plain name that is not built in is a file in the directory the server was started in: the name as
  given, then with `.xp`, then with `.map` added, as the C server does. So `--map mymap` finds
  `./mymap.xp`.
* A value with a path in it is a file, and only a file: `./default.xp`, `maps/mymap.xp`,
  `/opt/jxpilot/maps/war.xp`. A relative path is relative to the directory the server was started
  in. `.xp` and `.map` are tried here too when the name has no extension.

A built-in name wins over a file of the same name in the current directory: to play your own edited
`default.xp`, give `--map ./default.xp`. When nothing is found, the error lists the built-in names.

The server simulates at the map's `framesPerSecond` (default 14; many maps set their own). One
simulation step is one XPilot frame, so the game runs at the same speed as on an original server.

[[precedence-summary]]
=== Which setting wins

The same option can come from several places. From strongest to weakest:

. the command line;
. the map file;
. your config file;
. the defaults file, XPilot's `lib/defaults` (<<defaults-file>>);
. the built-in default.

An `\override:` value in the config file or the defaults file beats the map
(`gravity: \override: 0`). Details: <<06-config-and-maps.adoc#precedence,Precedence>>.

[[binding]]
== Network binding

JXPilot servers are often run on a VPN (WireGuard, a corporate tunnel, Tailscale), a LAN, or a public
host, and often on machines with several of these at once. The `bind` option says which local
addresses the server listens on.

[[bind-selectors]]
=== Bind selectors

`bind` takes one or more selectors, separated by commas or given by repeating `--bind`:

[cols="2,3,5",options="header"]
|===
|Selector |Example |Binds

|`all` (the default)
|`--bind all`
|Every address of every interface that is up, except IPv6 link-local addresses.

|`loopback`
|`--bind loopback`
|The loopback addresses (`127.0.0.1`, `::1`): only this machine can connect. Good for testing.

|IP address
|`--bind 10.224.0.16`, `--bind ::1`
|That one local address.

|CIDR network
|`--bind 10.224.0.0/22`, `--bind 100.64.0.0/10`
|Every local address inside the network. This keeps working when a VPN interface is renumbered
(`utun4` becomes `utun5`) or its address changes within the network.

|Interface name
|`--bind en0`, `--bind tailscale0`, `--bind if:utun4`
|Every address of that interface (except IPv6 link-local). `if:` forces the word to be read as an
interface name.

|Host name
|`--bind myhost.example.org`, `--bind host:vpn-name`
|The local addresses the name resolves to, at startup. `host:` forces the word to be read as a host name.

|Wildcard
|`--bind 0.0.0.0`, `--bind ::`
|The wildcard socket itself. Allowed, with a warning; see <<multi-homed>>.
|===

A bare word such as `en0` or `gameserver` is an interface name if such an interface exists, otherwise a
host name if it resolves, otherwise an interface name that may appear later (with a warning).

[[multi-homed]]
=== Replies from the right address

On a machine with several addresses, a server listening on a wildcard address (`0.0.0.0` or `::`) can
send its replies from a different address than the one the player contacted, for example from the LAN
address to a player who came in over the VPN. The player's computer then drops the replies and cannot
connect. Java offers no way to choose the reply address on a wildcard socket.

JXPilot avoids this. The selectors `all`, interfaces and CIDRs are turned into the concrete local
addresses they match, and the server opens one socket per address. Each player is tied to the socket
they first reached, and every reply goes out from that same address. So the default `all` is safe on
multi-homed machines; a literal `0.0.0.0` or `::` is allowed only because you asked for it, and the
server warns about it.

Notes:

* `::` alone also serves IPv4 (Java opens IPv6 sockets dual-stack). Giving both `0.0.0.0` and `::`
  binds only `::`, with a warning, because Linux refuses to bind both on one port.
* A wildcard and specific addresses cannot share a port; if both are given, only the wildcard is
  used, with a warning naming the dropped addresses.

[[rescan]]
=== Interfaces that come and go

When any selector is not a plain IP address (or `bindWait` is on), the server checks the network
interfaces every 3 seconds. It binds addresses that newly match (the VPN came up), closes sockets on
addresses that went away (the VPN dropped; players on it time out normally), and retries binds that
failed earlier. Plain IP addresses without `bindWait` are bound once at startup.

[[bind-wait]]
=== Selectors that match nothing: `bindWait`

By default, a selector that matches no local address at startup is an error, and the server exits:

----
bind warning: bind 'tailscale0' is neither a current interface nor a resolvable host name; treating it as an interface name
jxpilot server: bind selector(s) [if:tailscale0] match no local address (use bindWait to wait for them)
----

With `--bindWait` (or `bindWait: true` in the config file) the server starts anyway. If nothing at
all matches, it waits, checking every 3 seconds, until something does; selectors that match later are
bound by the rescan. Use this when the server starts before its VPN, for example at boot.

[[bind-examples]]
=== Examples

[cols="2,4",options="header"]
|===
|Situation |Command line
|Testing on your own machine |`--bind loopback`
|A home or office LAN |`--bind 192.168.1.0/24` (your LAN's network), or `--bind en0` / `--bind eth0`
|Tailscale only |`--bind 100.64.0.0/10 --bindWait` (or `--bind tailscale0 --bindWait`)
|A corporate VPN on `utunN` with `10.224.0.0/22` |`--bind 10.224.0.0/22 --bindWait`
|A public server |`--bind all` (the default), or its public address(es)
|VPN plus local testing |`--bind 100.64.0.0/10,loopback --bindWait`
|===

`bind` and `bindWait` can be set on the command line or in the config file, never in a map.

[[firewalls]]
== Ports and firewalls

A JXPilot server uses *one UDP port*, `contactPort` (default 15345), on every address it binds.
Players only need to reach that port; there are no TCP connections and no extra ports. (XPilot's
`clientPortStart` and `clientPortEnd` options are accepted but not used.)

Each datagram is at most 1200 bytes, so it fits VPN and IPv6 paths without fragmentation.

[cols="1,4",options="header"]
|===
|Firewall |Allow the port
|Linux, ufw |`sudo ufw allow 15345/udp`
|Linux, firewalld |`sudo firewall-cmd --permanent --add-port=15345/udp && sudo firewall-cmd --reload`
|Linux, nftables/iptables |`sudo iptables -A INPUT -p udp --dport 15345 -j ACCEPT` (or your nftables equivalent)
|macOS |The application firewall asks once whether `java` may accept incoming connections; allow it.
|Windows (PowerShell, as administrator)
|`New-NetFirewallRule -DisplayName "JXPilot" -Direction Inbound -Protocol UDP -LocalPort 15345 -Action Allow`
|Home router (NAT) |Forward UDP port 15345 to the server's LAN address.
|===

[[abuse-limits]]
=== Connection and traffic limits

These JXPilot options protect the server; all are in the
<<05-server-options.adoc#opts-network,option reference>>.

[cols="2,1,5",options="header"]
|===
|Option |Default |Meaning
|`maxClientsPerIP` (short `maxPerIP`) |2 |Players allowed from one IPv4 address or one IPv6 /64;
0 or less is unlimited. (XPilot's default is 2.)
|`ipPacketRate` |400 |Packets per second accepted from one address (IPv6: one /64) for connecting
and for packets outside a session.
|`ipPacketBurst` |800 |Burst size, in packets, for `ipPacketRate`.
|`sessionPacketRate` |400 |Packets per second accepted from one connected player.
|`sessionPacketBurst` |800 |Burst size, in packets, for `sessionPacketRate`.
|`snapshotDivisor` |1 |Send a snapshot every N simulation frames (1 = every frame).
|`radarDivisor` |3 |Include the radar in every Nth snapshot.
|`denyHosts` |none |Addresses whose connection attempts are ignored, separated by commas, semicolons or
spaces: an IP address, `address/prefix` (`203.0.113.0/24`, `2001:db8::/32`) or, as in XPilot,
`address/dotted.mask` (`203.0.113.0/255.255.255.0`). Host names are not resolved.
|`bind` |`all` |See <<binding>>. Without `--bind`, XPilot's `serverHost` (a host name or address) is
used as the bind selector.
|`bindWait` |false |See <<bind-wait>>.
|===

All of these can be set on the command line or in the config file, but not in a map. A player that
sends nothing for 10 seconds, or does not acknowledge reliable messages for that long, is dropped.

[[joining]]
== Joining, leaving and full servers

The Java server admits players as the XPilot server does:

* *Slots.* A map has one player slot per home base, shared by humans and robots.
* *Full game.* When a human joins a full game, a robot is removed to make room
  (`"NAME" upset the gods and was kicked out of the game.`). With no robots left, every paused human is
  removed instead (`The paused "NAME" was kicked because the game is full.`). Otherwise the join is
  refused.
* *Names.* A name must not be empty or already in use, compared without regard to case. Names are cut
  to 16 characters.
* *Teams.* In team play a player asks for a team (the client's `--team`). With `teamAssign` (the
  default) the server picks one when none is given; without it, a player who gives no valid team is
  refused. A full team makes room the same way as a full game, by removing one of its robots, then its
  paused players (`... was kicked because team N is full.`).
* *Welcome.* The first player sees `Welcome to "MAP", made by AUTHOR.`; everyone sees later arrivals as
  `NAME has entered "MAP", made by AUTHOR.` (with `(team N)` in team play).

When the server refuses a player, the client shows `Rejected by SERVER:` and one of these reasons:

[cols="2,4",options="header"]
|===
|Reason |Why
|`server is full` |No slot, and no robot or paused player to remove; or the requested team is full.
|`too many players from your address` |More than `maxClientsPerIP` players from one address.
|`name not accepted` |The name is empty or already in use.
|`incompatible version` |The client speaks another JXPilot protocol version.
|`join refused` |Team play without a valid team, and `teamAssign` is off.
|===

The server removes players with these reasons, shown to the player when they are disconnected:

[cols="2,4",options="header"]
|===
|Reason |Why
|`auto-kicked: paused too long` |Paused for longer than `maxPauseTime` seconds (default 3600).
|`no pause with full game`, `no pause with full team` |Paused while a newcomer needed the slot.
|`no free base` |No base was free when the player was ready to enter.
|(timeout) |Nothing received from the player for 10 seconds.
|===

[[handshake]]
=== The connection handshake

A UDP server can be abused to flood a third party: an attacker sends small requests with a forged
source address, and the server sends its answers to the victim. The JXPilot server is not useful for
that:

. The client sends CONNECT.
. The server answers with a small ACCEPT that carries a session number, and nothing else. It repeats
  the ACCEPT after 250, 500 and 1000 ms, and forgets the request about 3.75 seconds after the first.
  Every ACCEPT is smaller than the CONNECT it answers.
. The client proves that it really is at its address by answering with the session number. Only then
  does the server send the map and the game.

For operators this means: a client behind a firewall that blocks the replies cannot even start; and a
burst of unanswered connection attempts in a log is harmless. CONNECTs also count against
`ipPacketRate`.

[[defaults-file]]
== The defaults file: XPilot's `lib/defaults`

The XPilot server reads a defaults file, `lib/defaults`, at every start, and so does the JXPilot server:
the jar carries XPilot 4.5.5's file, unmodified. Like XPilot, the server reads its sources in this
order: the command line, the defaults file, your config file, then the map. The precedence rules above
then decide: the command line beats everything, the map beats the defaults file, and a defaults or
config value written with `\override:` beats the map.

What `lib/defaults` changes, compared with the built-in defaults of the option reference:

* `gravity -0.25` (built in: -0.14);
* `allowModifiers` on (built in: off); it also sets `allowNukes` and `allowClusters` off and
  `framesPerSecond 14`, the same as the built-in values;
* item appearance: `maxItemDensity`, `movingItemProb 0.3` and most of the individual `item...Prob`
  values (not armor, mirror, deflector, hyperjump or phasing);
* through `expand: SoftWalls`, wall bounce speeds and angles of 180 (`maxShieldedWallBounceSpeed`,
  `maxUnshieldedWallBounceSpeed`, `maxShieldedPlayerWallBounceAngle`,
  `maxUnshieldedPlayerWallBounceAngle`): softer walls.

A map that sets any of these keeps its own value; `default.xp`, for instance, keeps its own bounce
speeds and its 12 frames per second. The option reference shows the `lib/defaults` values next to the
built-in ones.

`lib/defaults` also defines three groups of settings you can switch on with `-expand NAME` (or
`expand: NAME` in your config file):

[cols="2,5",options="header"]
|===
|Group |Settings
|`PrivateSettings` |`idleRun` off, `noQuit` off, no meta server, `contactPort 15000`, `serverHost localhost`
|`PublicSettings` |`idleRun` on, `noQuit` on, `reportToMetaServer` on
|`BounceAll` |Everything bounces off walls (shots, balls, mines, items, sparks, debris, asteroids, players),
with softer bounce limits, and `edgeBounce` on
|===

`--defaults FILE` reads your own file instead (start from a copy of XPilot's: it is in the source as
`server/src/main/resources/xpilot/defaults`), and `--defaults none` reads none, so the built-in defaults
apply. A file you name that cannot be read stops the server with an error.

[[config-files]]
== Configuration files

A server configuration file uses the same `name: value` format as map files
(<<06-config-and-maps.adoc#file-format,File format>>), so any option can be set there, except the few
marked as command-line only in the option reference. Pass the file as the last argument:

[source,shell]
----
java -jar jxpilot-server-VERSION.jar --map teamball /etc/jxpilot/server.conf
----

An example:

[source,text]
----
# /etc/jxpilot/server.conf
port:            15345
bind:            100.64.0.0/10, loopback   # Tailscale plus local testing
bindWait:        true                      # start before the VPN is up
maxClientsPerIP: 8
gravity:         \override: -0.2           # beats the map's own gravity
----

Of XPilot's other file options, `defaults` (`--defaults`) and `adminMessage`
(<<admin-messages>>) are used; `passwordFileName`, `motd` and `scoretable` are accepted but not read.

[[admin-messages]]
=== Messages to the operator: `god:`

A player who types a chat line starting with `god:` writes to the operator rather than to the other
players. As in XPilot, the line is appended to the file named by `adminMessageFileName` (short
`adminMessage`), with the date, time and player name, if that file already exists and is writable, and
only while the file stays below `adminMessageFileSizeLimit` bytes (default 20202). Without the option
the line is dropped.

[[robots]]
== Robots

The Java server has XPilot's default robot, ported from the C server: it hunts players, dodges walls,
shields, refuels and declares war on whoever killed it. Robots look like human players; the score list
marks them `R`.

Robots play only while at least one human is in the game, unless `rawMode` (short for `idleRun`) is on,
in which case the game, and the robots, run even when nobody is connected.

[cols="2,1,5",options="header"]
|===
|Option |Default |Meaning
|`maxRobots` (short `robots`) |4 |Robots join while fewer than this many players (humans and robots)
are in the game and a base is free. `0` turns robots off.
|`minRobots` |-1 |At least this many robots stay in the game, if there is room (never more than
`maxRobots`).
|`robotsTalk` |false |Robots taunt when they kill, die or declare war.
|`robotsLeave` |true |Robots retire after `robotLeaveLife` lives or leave when their score drops below
`robotLeaveScore` or their kill ratio below `robotLeaveRatio` (`NAME retired.`,
`NAME left out of disappointment.`). New ones take their place.
|`robotTeam` |0 |In team play with `restrictRobots`, the team robots join.
|`restrictRobots` |true |Robots only join `robotTeam`.
|`reserveRobotTeam` |true |Humans may not join the robot team.
|`robotFile` |XPilot's robots |A file of robot personalities (below). Command line or config file.
|`logRobots` |true |Log each robot that joins: `NAME (PLAYERS, robot) starts at startpos BASE.`
|===

With limited lives, a robot that loses its last life leaves the game and is replaced by a new one
(outside race and team play, or when its score is too low), instead of waiting out the round. Robots
react to how they were killed as in XPilot: killed by a weapon or a shove, a robot declares war on its
killer; when two ships destroy each other in a collision, robots at war with the other stop that war.

The full list, with every robot option, is in <<05-server-options.adoc#opts-robots,Robots>>.

[[robot-file]]
=== Robot personalities: `robotFile`

Robots get their names, ship shapes and characters from a list of personalities. The built-in list is
XPilot 4.5.5's `lib/robots` file, with 38 robots (Mad Max, Blackie, Kryten, Marvin, R2D2, ...).
`robotFile` replaces it with your own file in the same format: one record per robot, records separated
by blank lines.

[source,text]
----
type:   default
para:   94 20
ship:   (15,8,7)(15,0)(7,1)(7,2)(2,4)(-1,11)(-3,11)(-2,3)(-8,6)(-8,-6)(-2,-3)(-3,-11)(-1,-11)(2,-4)(7,-2)(7,-1)
name:   Mad Max

type:   default
para:   10 90
ship:   (16,6,10)(15,0)(6,2)(-2,3)(-1,4)(-2,5)(-10,8)(-13,8)(-13,1)(-15,0)(-13,-1)(-13,-8)(-10,-8)(-2,-5)(-1,-4)(-2,-3)(6,-2)
name:   Blackie
----

`type:` is the robot type (`default` is the only one), `para:` its attack and defense (0 to 100),
`ship:` a ship shape in XPilot's format and `name:` the name players see. A record without a `name:`
is ignored, and a field left out keeps the value of the previous record. If the file cannot be read,
or has no named record, the built-in list is used.

[[hosting]]
== Hosting for friends far away

A JXPilot server is small. Measured with six robots on `default.xp`, it uses about 50-60 MB of memory
(resident) and under 1% of one CPU core. A virtual machine with 256 MB of memory is plenty; give Java
`-Xmx128m`.

* *One port.* Everything goes over one UDP port, the default 15345, or the one you set with `--port`.
  Open that port in the firewall (<<firewalls>>), and nothing else.
* *Where to host.* Every player's game lags by their round trip time to the server. For players on
  different continents, a cheap cloud VM roughly half way between them is fairer and smoother than a
  home server at one end: two players with 150 ms to a server in the middle each lag 150 ms, while a
  server at one player's home gives the other the whole 300 ms.
* *Today's lag.* Your own ship reacts to your keys after about one round trip plus 135 ms. Making that
  faster with client-side prediction is planned; see
  https://github.com/awkay/jxpilot/blob/main/docs/latency-fixes.md[docs/latency-fixes.md].
* *Run it as a service* so it survives logouts and reboots (<<service>>), and give friends the address
  from the `listening on` lines.

A minimal setup on a fresh Linux VM:

[source,shell]
----
java -XX:+UseZGC -Xmx128m -jar jxpilot-server-VERSION.jar --map default -robots 4 -noQuit
----

[[service]]
== Running as a service (systemd)

On Linux, run the server as a systemd service under its own user. Set it up once:

[source,shell]
----
sudo useradd --system --home /opt/jxpilot --shell /usr/sbin/nologin jxpilot
sudo mkdir -p /opt/jxpilot /etc/jxpilot
sudo cp jxpilot-server-VERSION.jar /opt/jxpilot/jxpilot-server.jar
sudo cp server.conf /etc/jxpilot/server.conf
----

Then create `/etc/systemd/system/jxpilot.service`:

[source,ini]
----
[Unit]
Description=JXPilot server
Wants=network-online.target
After=network-online.target
# On a VPN, also wait for it, e.g.: After=tailscaled.service (and use bindWait)

[Service]
Type=simple
User=jxpilot
Group=jxpilot
WorkingDirectory=/opt/jxpilot
ExecStart=/usr/bin/java -XX:+UseZGC -Xmx256m -jar /opt/jxpilot/jxpilot-server.jar \
    --map default -noQuit /etc/jxpilot/server.conf
# Java exits with 143 after SIGTERM (systemctl stop): that is a clean stop.
SuccessExitStatus=143
Restart=on-failure
RestartSec=5
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
----

Start it, enable it at boot, and read its log:

[source,shell]
----
sudo systemctl daemon-reload
sudo systemctl enable --now jxpilot
journalctl -u jxpilot -f
----

To change the map, edit `ExecStart` (or set `mapFileName:` in the config file) and run
`sudo systemctl restart jxpilot`. Adjust `/usr/bin/java` if Java 25 is installed elsewhere
(`readlink -f "$(which java)"`).
